# ERM «Фасады Сысолы» — Business Requirements v1.0

---

# 1. 🎯 Назначение системы

Система предназначена для управления производством фасадов:

- ведение заказов
- контроль этапов производства
- расчёт стоимости фасадов
- генерация раскроя
- учёт трудозатрат
- анализ узких мест производства (по этапам)

---

# 2. 👥 Роли пользователей

## 2.1 Администратор
- полный доступ к системе
- управление пользователями
- управление заказчиками
- управление заказами и этапами

## 2.2 Работник (цех)
- просмотр и обработка заказов
- изменение статусов внутри этапа (UI-only)
- перенос заказов между этапами (канбан)
- внесение трудозатрат (time tracking)
- не привязан к конкретному этапу

## 2.3 Заказчик (роль пользователя)
- отдельная сущность **заказчик** (компания / контрагент), к которой привязаны заказы
- пользователи с ролью «заказчик» привязаны к этой сущности; у одного заказчика **несколько пользователей**
- все пользователи одного заказчика видят **все заказы** этого заказчика (read-only)
- вход в систему только у тех, кому выдали учётную запись; карточка заказчика в справочнике может существовать без привязанных пользователей
- без доступа к управлению производством, этапами, раскроем и административным справочникам

---

# 3. 🧱 Сущность: Заказ

## 3.1 Поля заказа
- номер заказа (автоинкремент, отображение с ведущими нулями с **000001**; при исчерпании шести цифр номер **продолжает расти** — 7 и более цифр)
- дата создания
- дата дедлайна
- заказчик
- текущий этап
- комментарий
- итоговая стоимость

## 3.2 Принцип системы
> Заказ = единственная процессная сущность

---

# 4. 🏭 Производственный процесс (этапы)

## 4.1 Этапы (канбан-точки)

Пример **стартового** набора (фактический список задаётся в БД и может отличаться):

- Новый (входная стойка)
- Раскрой
- Подготовка
- Покраска / Плёнка (камера)
- Полировка / Шлифовка
- Упаковка
- Отгрузка (выходная стойка)

## 4.2 Свойства этапов
- список этапов и **порядок** хранятся в БД
- администратор может **менять порядок**, **добавлять и удалять** этапы из админки
- у заказа в каждый момент времени ровно **один текущий этап**
- этап = физическая точка производства

## 4.3 Канбан-переход
- ручной перенос пользователем (цех / админ по правилам роли)
- переходы **в любую сторону** допускаются (в т.ч. возврат на доработку)
- новый заказ создаётся в этапе **«Новый»**

---

# 5. 🏷 Внутренний статус этапа (UI-only)

## 5.1 Статусы
- В работе
- Заблокирован
- Готов

## 5.2 Правила
- не влияет на бизнес-логику
- не влияет на переходы
- не участвует в аналитике
- может не использоваться

## 5.3 Назначение
- визуализация состояния внутри этапа

---

# 6. 🧱 Сущность: Фасады

## 6.1 Поля
- фрезеровка
- покрытие
- цвет
- размеры (мм)
- толщина (мм)
- интегрированная ручка
- радиус завала торца
- дополнительные опции (text)

## 6.2 Цена
- **базовая цена** считается **на фронтенде** по данным, внесённым в заказ (фасады и поля заказа)
- **переопределение** (процент, фиксированная сумма и т.п.) — дополнение для скидки, наценки и нестандартных случаев; итоговая сумма хранится/передаётся в API вместе с заказом
- итоговая цена заказа

## 6.3 Роль
- данные заказа
- не участвует в процессе
- не имеет статусов

---

# 7. 🪵 Модуль «Раскрой»

## 7.1 Принцип
> Stateless операция над заказом

- не сохраняется
- пересчитывается с нуля

## 7.2 Вход
- заказ
- фасады

## 7.3 Логика
1. группировка:
    - материал (MVP: MDF)
    - толщина
2. раскрой по группам
3. каждая группа = отдельная страница

## 7.4 Выход
- набор страниц раскроя
- схемы размещения

## 7.5 Ограничения MVP
- нет остатков
- нет версий
- нет сохранения результата раскроя и PDF на сервере (PDF **генерируется на сервере** библиотекой и **отдаётся потоком** в ответе; на диск и в хранилище заказа не пишется)
- нет редактирования

## 7.6 UI и доступ
- кнопка “Раскрой”
- новая вкладка
- визуализация
- PDF: запрос к API → **сервер** (библиотека) формирует PDF → отдача потоком в HTTP-ответе → браузер скачивает / открывает; без записи на диск и в файловое хранилище заказа
- **доступ к раскрою и PDF:** администратор и работник (цех); заказчик — нет

# 9. ⏱ Time Tracking

## 9.1 Принцип
- ручной ввод времени
- без автоматизации

## 9.2 Time Entry
- заказ
- пользователь
- этап
- время
- комментарий
- дата

## 9.3 Возможности
- множественные записи
- задним числом
- привязка к этапу

## 9.4 Валидация (MVP)
- основная валидация полей — **на фронтенде**; правила на backend при необходимости ужесточаются позже

---

# 10. 📊 Метрики

## Принцип
> Метрики считаются только по этапам

## 10.1 Заказные метрики
- **lead time (рабочее определение):** от момента **создания заказа** до момента **последнего этапа / завершения потока** — детализация «что считать финишем» при внедрении метрик
- просрочки
- общее время

## 10.2 Этапные метрики
- очередь
- время обработки
- загрузка
- узкие места — **правила расчёта позже**, на MVP не фиксируется

## 10.3 Ограничения
- нет метрик по статусам
- нет внутриэтапной аналитики

---

# 11. 📜 Audit Log

Фиксируется:
- смена этапа
- изменения заказа
- изменения фасадов
- изменения цены

Поля:
- пользователь
- время
- тип изменения
- описание изменения **в человекочитаемом виде** (текст; не обязательно машинный JSON-diff)

## 11.1 Доступ
- просмотр истории (audit log) — **только администратор**

---

# 12. 💰 Ценообразование

- динамическое
- может изменяться в любой момент
- не фиксируется окончательно
- базовая величина считается на клиенте по содержимому заказа; сервер хранит введённые данные и итоги, переопределения

---

# 13. 🧾 Заказчики

- сущность в справочнике (компания / контрагент), привязка к заказам
- несколько **пользователей** с ролью «заказчик» на одну сущность заказчика; все они видят заказы этой организации
- учётная запись выдаётся явно; без учётки возможна только карточка в справочнике без входа в кабинет

---

# 14. 🖥 UI модули

- список заказов
- карточка заказа
- канбан этапов
- модуль раскроя
- пользователи
- заказчики (справочник для админа)
- кабинет заказчика: заказы своей организации (просмотр)

---

# 15. ⚠️ Ограничения MVP

- нет авто-трекинга времени
- нет сохранения раскроя и PDF раскроя на сервере
- нет остатков материалов
- нет сложной оптимизации
- нет AI/прогнозирования
- нет версионирования заказов
- нет обязательных статусов

---

# 16. 🧠 Архитектура

## Слои

### 4. Time Entries (факты)

## Принципы системы

- заказ = поток

# 🏁 Итог

Система представляет собой production-oriented order management system для цеха фасадов с физическим потоком заказов через этапы, stateless расчётом раскроя и событийным учётом времени.
